# ADR-0021：授权请求按"人读的样子"生成，助理可以选择发到哪个平台

状态：Accepted · 日期：2026-11-12 · 相关：[../40-plan/11-console-approvals-schedules.md](../40-plan/11-console-approvals-schedules.md) · [../10-architecture/14-security-and-permissions.md](../10-architecture/14-security-and-permissions.md) §3 · [ADR-0015](ADR-0015-permission-modes-and-auto-review.md)

## 背景

1. **请求看不懂。** 发给主人的是 `Approval a12 requested: shell_exec {"command":"…` 加 `Reply /approve a12`：工具名、截断的原始 JSON、ISO 时间，决定要手打编号。三个连接器各抄了一份这句话，网页再用正则把它解析回来。库里只存 400 字摘要，控制台也只能显示这一行。
2. **没有理由。** 直接调用被拦下时请求里没有"为了什么"，助理只好再发一条消息解释，主人收到两条。
3. **只能广播。** 请求固定发给所有能投递的平台，助理不能选，也不知道发到了哪里。
4. **决定之后没有下文。** 原消息不变，其他平台不知道已经处理；请求过期也不通知助理。

## 决策

### 1. 核心生成结构化的请求，所有地方从它渲染

- 创建请求时生成 `ApprovalView { title, target?, fields[], reason?, held?, family }`，脱敏后存进 `approvals.view_json`，并随 `approvals/request` 发给插件。`summary` 改为由它生成的一行人话（旧插件照常可用）。
- `title` 与字段来自工具的声明 `approval: { title, target, fields }`（`ToolSpec` 与进程外插件的工具声明都有；纯声明，不执行代码）；MCP 工具用服务器给的标题；都没有时用工具名和标量参数。文字用 `daemon.language`。
- 另存一份脱敏后的完整输入（`input_json`，上限 8000 字符），控制台可以展开看。
- **参数值是数据**：每个值压成一行、截断、去掉不可见的方向控制符，只当纯文本显示。工具输入里的换行不能冒充请求的另一行。
- 编号（`a12`）只用于审计、API 和事件；请求里不出现，主人不需要输入它。

### 2. 决定是点一下，或者一个不会被误解的词

- `@protea/plugin-sdk` 的 `ApprovalInbox` 负责文字、按钮和回复词，连接器只管发送：QQ 用官方消息按钮（被拒时降级为文字），Telegram 用 inline keyboard，微信用文字加回复词，网页用卡片。
- 选项固定三个：同意、同意并在一段时间内不再问这一组工具（`permissions.grantMaxMs` 为 0 时没有）、拒绝。拒绝可以带一句话，写进 `approval.decided`。
- 没有按钮时的回复词（同意 / 拒绝 / yes / no 等）只在不可能指别的事时才算决定：消息引用了请求；或带了请求的编号；或整条消息就是一个回复词，且这个平台上只有一个待定请求，且它是机器人在这个平台发出的最后一条消息。否则照常作为对话交给助理。`/approve <id>` 保留，不再提示。
- 请求被决定或过期时，宿主用通知 `approvals/resolved` 告诉所有显示过它的插件，由它们撤掉按钮或改写消息。

### 3. 助理可以选平台，默认广播

- 策略为 `ask` 的工具在给模型的 schema 里多一个保留输入 `_approval: { reason?, platforms? }`。分发器在校验、求哈希、执行和审计之前把它摘掉，所以它不影响"用同样的输入再调一次"。
- `approval_request` 增加 `platforms`。对一个还在等的请求再调一次（同样的工具与输入），可以补理由，或在别的平台再显示一次。
- 不给 `platforms` 就发给所有能显示请求的平台。给了就只发这些；它们都没送达时自动改发其余平台。回执写明实际发到了哪里。
- 平台只决定通知发到哪。网页对话的卡片和控制台读的是请求状态，始终显示全部待定请求；主人在任何平台都能决定。

### 4. 请求过期要告诉助理

待定的请求过期时推一条 `approval.expired`（L3）。已同意但没有执行就过期的不通知。

## 备选方案

- **让模型（或便宜的模型）把参数改写成人话。** 多一次调用和延迟，而且改写的内容不再是将要执行的内容。声明式的标题加原样的参数值更可靠。
- **不注入 `_approval`，理由和平台只能通过先调 `approval_request` 给出。** 直接调用被拦下时仍然没有理由、只能广播，而这是最常见的路径。
- **拦下后不立即发请求，等模型补充理由后再发。** 模型忘了补，主人就永远收不到请求；为此还要给请求加一个"未发出"的状态。
- **任何时候都认"同意"。** 主人回答助理别的问题时说一句"好"或"同意"，会被当成批准一条几分钟前的请求。

## 后果

- 每个需要审批的工具的 schema 多几十个 token；策略变化时系统前缀变化一次。
- 协议是加法：`ApprovalRequestParams.view` / `grantMaxMs`、`ApprovalDecideParams.note`、`approvals/resolved`、工具声明的 `approval`。不认识这些的插件行为不变。
- 迁移 11 给 `approvals` 加四列；旧行没有 `view`，界面退回显示 `summary`。
- 回复词的待定列表在连接器内存里：连接器重启后，一句"同意"重新变回普通消息，按钮、控制台和 `/approve <id>` 仍然有效。
- QQ 官方按钮在真实账号下的表现、真实模型是否恰当地填写 `_approval`，留给实测（T18）。
