# ADR-0022：上线前不做向前兼容，只用最合适的方案

状态：Accepted（**上线时必须由新的 ADR 取代**）· 日期：2026-11-12 · 相关：[ADR-0023](ADR-0023-plugin-tools-on-demand.md) · [../40-plan/01-roadmap.md](../40-plan/01-roadmap.md) M7a

## 背景

Protea 还没有上线：没有发布过镜像（M7a），没有外部用户，数据卷只在开发者自己的机器上。

一个名字或配置项起得不对时，兼容的做法是保留旧名作别名、加弃用告警、写迁移代码。上线后应该这样做，但现在这么做只有成本：代码多出兼容分支，文档里两套说法并存，测试要覆盖两条路径，而这些代价没有换来任何人受益。例如 MCP 按需加载的元工具 `mcp_search` / `mcp_call` 推广到插件后名字已经不准确（[ADR-0023](ADR-0023-plugin-tools-on-demand.md)），保留它们只是为了兼容几段开发期的对话历史。

## 决策

在上线（发布 `v1.0.0` 和第一个公开镜像）之前：

1. **只按最合适的方案改**。工具名、配置键、控制接口的路径与字段、插件协议的方法与字段、系统段的 id、CLI 子命令都可以直接改名或删除：不留别名，不写兼容分支，没有弃用期，不为旧配置键给出告警。
2. **一次改完，不遗留**。同一个 PR 里把代码、测试、文档、默认人格与 Skills 里的引用一起改掉，仓库里不再出现旧名字。例外是历史记录：已有的 ADR 和 `docs/40-plan/` 下的方案文档记录的是当时的决定，不改写，只在开头注明被哪一篇修订。
3. **已有的开发实例手动处理**。改动影响开发机上的 `config.yaml` 或数据卷时，在 PR 说明里写清楚要手动改什么；不为此写迁移代码。数据库的结构迁移照旧按编号追加（这是已有机制，用来建表和加列，不是兼容层）。

**上线时要改**：发布 `v1.0.0` 之前，用一篇新的 ADR 取代本篇，改为"破坏性改动要有迁移、别名或弃用期，并写进变更记录"。M7a 的清单里有这一项。

## 备选方案

- **现在就按上线后的标准做兼容**：每次改名都留别名和告警。代价如上，而且等真正上线时，这些别名本身也成了要清理的历史包袱。
- **每次改动单独判断要不要兼容**：判断的标准说不清，结果多半是"保留一下比较稳妥"，最后和上一条一样。

## 后果

- 改动更干净：一个概念在代码和文档里只有一个名字。
- 开发机上已有的实例可能在升级后需要手动改配置；旧的对话历史里可能引用已经不存在的工具名，模型按"工具不存在"处理，不需要特殊照顾（必要时交接或清空会话）。
- 这条规则有明确的终点：上线前必须被取代。忘记取代的风险由 M7a 清单里的一项来防。
