# ADR-0015：权限模式与 auto 判断模型

状态：Accepted · 日期：2026-11-10 · 相关：[../10-architecture/14-security-and-permissions.md](../10-architecture/14-security-and-permissions.md) §2 · [ADR-0013](ADR-0013-sandboxed-shell-and-in-container-browser.md) · [../40-plan/08-sandbox-browser-vision.md](../40-plan/08-sandbox-browser-vision.md) §6

## 背景

沙箱 shell 和浏览器的工具默认都要审批。逐次审批适合少量操作，一个几十步的任务要点几十次；时限授权又是整组工具放行，不看具体内容。主人决定默认保持 `ask`，同时提供可以切换的模式，并参考 Claude Code 的做法做一个能接判断模型的 auto 模式。

## 决策

- **策略不变，模式只决定 `ask` 的调用由谁放行。** 策略仍是 `allow` / `ask` / `deny`；`deny` 在任何模式下都拒绝，`allow` 不受模式影响。
- **四个模式**：`ask`（默认，逐次问主人）、`auto`（判断模型放行，没放行的转给主人）、`bypass`（直接执行，照常审计）、`locked`（一律不执行，也不打扰主人）。
- **判定顺序**（策略为 `ask` 时）：`locked` → 拒绝；有一次性批准或有效的时限授权 → 执行；是主人在 `permissions.tools` 里显式写的 `ask`（钉住）→ 问主人；然后按模式：`ask` 问主人，`bypass` 执行，`auto` 交给判断模型。
- **判断模型只有两种结论**：`allow` 或 `ask`。没放行时转给主人审批并附上理由，不直接拒绝：Protea 的审批本来就是异步的，不会卡住助理，所以 auto 的保护不低于 `ask`。
- **判断模型看到的内容受限**：内置准则、主人写的三段常驻规则（`permissions.auto.environment` / `allow` / `ask`）、主人最近的消息、这批工作是谁触发的（第三方的正文不给）、本批已发出的工具调用，以及待判断的这一次。看不到工具回执、网页和文件内容、第三方消息、助理的文字和理由、记忆——这些是注入的来源，记忆还是助理自己能写的。
- **任何失败都按 `ask` 处理**：超时、报错、输出不是一个完整的 JSON 对象、输出被截断、预算用完、输入太长（超过 16000 字符，放不下完整内容就不判断）。
- **连续 3 次或一小时内 20 次没放行，auto 自动暂停**，实际模式回到 `ask`，通知主人一次，直到主人再次设置模式。
- **模型角色新增 `judge`**，默认用主模型；可以用 `providers.roles.judge` 和 `models.judge` 换供应商或模型。判断请求照常经过脱敏、录制和用量统计。代码里是 `PermissionJudge` 接口，以后接专门的分类服务只需换实现。
- **切换只有主人能做**：Telegram `/mode`（校验方式与 `/approve` 相同）、`protea mode`、控制台审批页、`POST /api/permissions/mode`。助理没有切换模式的工具。
- **不带时限的切换改基线**（写进 `config.yaml` 的 `permissions.mode`）；带时限的是临时覆盖，到期回到基线，重启后仍有效。`bypass` 必须带时限，不能写成基线，上限沿用 `permissions.grantMaxMs`。

## 备选方案

- **没放行时直接拒绝（Claude Code 的做法）**：不打扰主人，但误判时助理没有出路。Claude Code 是同步交互，主人就在终端前；Protea 的主人常常不在。
- **两阶段判断（快速过滤 + 带推理复核）**：Claude Code 这样做是为了省成本。这里只有 `ask` 的调用才到判断模型，量很小，一阶段足够。
- **派生 Fork 时和 Fork 返回时做整体审查**：只做逐次判断。Fork 的调用走同一个守卫，判断模型能看到发起它的批的触发者和调用。
- **把工具回执也给判断模型，以便核实参数来源**：判断更准，但工具回执是注入的主要入口，等于让被判断的内容影响判断。
- **让模型用工具调用输出结论**：`ProviderRequest` 没有强制工具的通用字段，各协议的兼容程度也不同。用严格的 JSON 文本：整段回复必须是这个对象，否则按 `ask`。
- **把判断规则也放进数据库**：`config.yaml` 已能热更新，也更容易审阅。

## 后果

- 每个到判断模型的调用多一次模型请求，延迟是秒级；费用记在 `judge` 角色上，计入批的等级预算。
- `ask` 模式下的行为与之前完全相同。
- 残余风险：
  - 判断模型会漏判。Anthropic 公布的 Claude Code 分类器在真实越界操作上的漏判率是 17%，自己配的模型没有评测，不会更好，模型太弱时更差。
  - 判断模型看不到回执，分不清输入里的网址或 ID 是查出来的还是编的。
  - auto 依赖主人最近的消息作为授权依据；定时任务和第三方触发的工作没有这个依据，只能靠常驻规则，覆盖不到的都转给主人。
  - 想让某个操作永远经过主人，要写成 `permissions.tools` 里的 `ask`（钉住）。
